# Glossaire et mindmap Anthropic

Glossaire du cours Anthropic « Introduction to agent skills » (Claude Certification, Developer Foundation). Il se suffit à lui-même : un terme que définit aussi un autre cours a ici sa propre entrée, telle que ce cours le définit. Définitions en anglais, résumées du cours ; traduction française entre parenthèses, vérifiée sur des sources françaises de l'IA et de l'informatique (documentation des éditeurs, terminologie officielle, recherche).

Schémas, avec un sommaire et une légende pour chacun : [mindmap.md](mindmap.md).

## Glossaire

### Skill *(Skill)*

A markdown file that teaches Claude how to do something once; Claude then applies that knowledge automatically whenever it's relevant. Skills fix repeating yourself: explaining your team's coding standards to Claude, re-describing how you want feedback structured on every PR review, reminding Claude of your preferred commit message format. Skills are folders of instructions and resources that Claude Code can discover and use to handle tasks more accurately. Each skill lives in a SKILL.md file with a name and description in its frontmatter; below the frontmatter go the actual instructions (a review checklist, formatting preferences, whatever Claude needs to know for that task). To create one, make a directory named after the skill inside the skills folder, then a SKILL.md file inside it, in two parts separated by frontmatter dashes: the name identifies the skill; the description tells Claude when to use it, its matching criteria; everything after the second set of dashes is the instructions Claude follows when the skill is activated. The description is how Claude decides whether to use the skill: Claude reads your request, compares it to all available skill descriptions, and activates the ones that match; the terminal shows the skill load. How the match works: [skill matching](#skill-matching-correspondance-des-skills). Skills are unique among Claude Code's ways to customize behavior because they're automatic and task-specific. [CLAUDE.md](#claudemd-claudemd) files load into every conversation (if you want Claude to always use TypeScript's strict mode, that goes in CLAUDE.md); skills load on demand when they match your request. Claude only loads their name and description initially, so they don't fill up your entire context window: a PR review checklist doesn't need to be in context while you're debugging, and loads when you actually ask for a review. Slash commands require you to explicitly type them; skills don't: Claude applies them when it recognizes the situation. Skills work best for specialized knowledge that applies to specific tasks: code review standards your team follows, commit message formats you prefer, brand guidelines for your organization, documentation templates for specific types of docs, debugging checklists for particular frameworks. The rule of thumb: if you find yourself explaining the same thing to Claude repeatedly, that's a skill waiting to be written. Skills are stored in different places depending on who needs them: [personal skills](#personal-skills-skills-personnels) and [project skills](#project-skills-skills-de-projet). To update a skill, edit its SKILL.md file; to remove one, delete its directory. Claude Code watches your skills directories, so a new skill or a change is picked up in the current session, without a restart; if the .claude/skills folder in your home directory didn't exist when the session started, Claude Code isn't watching it yet: run /reload-skills, and again after each later change. The available skills list shows whether a skill is available. Two skills with the same name: [skill priority](#skill-priority-priorité-des-skills). Its frontmatter's fields: [skill metadata fields](#skill-metadata-fields-champs-de-métadonnées-des-skills); a larger skill's files: [progressive disclosure](#progressive-disclosure-divulgation-progressive). Skills add knowledge to your current conversation: when a skill activates, its instructions join the existing context, and the expertise applies throughout a conversation. They're request-driven: they activate based on what you're asking. Use them for task-specific expertise, knowledge that's only relevant sometimes, detailed procedures that would clutter every conversation, knowledge that informs how Claude handles requests, and guidelines that affect Claude's reasoning. Claude Code's other customization options solve different problems: [CLAUDE.md](#claudemd-claudemd), [subagents](#subagent-sous-agent), [hooks](#hook-hook) and [MCP servers](#mcp-server-serveur-mcp). Each handles its own specialty: don't force everything into skills when another option fits better, and you can use multiple at a time. A typical setup might include CLAUDE.md for always-on project standards, skills for task-specific expertise that loads on demand, hooks for automated operations triggered by events, subagents for isolated execution contexts for delegated work, and MCP servers for external tools and integrations. Use skills when you have knowledge that Claude should apply automatically when the topic is relevant. Skills become much more valuable when they're shared: a PR review skill that only you use is helpful, but the same skill shared across your entire team standardizes code review and creates a consistent experience across your organization. Three ways to distribute them: [project skills](#project-skills-skills-de-projet) committed to a repository, [plugins](#plugin-plugin), and [managed settings](#managed-settings-paramètres-gérés). A [subagent](#subagent-sous-agent) doesn't see the skills you've already invoked.

### Personal skills *(Skills personnels)*

The [skills](#skill-skill) that go in the `.claude/skills` folder in your home directory (on Windows too, in your user folder). They follow you across all your projects: your commit message style, your documentation format, how you like code explained.

### Project skills *(Skills de projet)*

The [skills](#skill-skill) that go in `.claude/skills` inside the root directory of your repository. Anyone who clones the repo gets them automatically. This is where team standards live, like your company's brand guidelines, preferred fonts, and colors for web design. They get committed to version control alongside your code, so the whole team shares them. Committing skills directly to your repository is the simplest sharing method, with no extra installation needed: when you push updates, everyone gets them on the next pull. It works well for team coding standards, project-specific workflows, and skills that reference your codebase structure. The .claude directory contains your agents, hooks, skills, and settings, all version-controlled and shared with the team through normal Git workflows.

### Skill matching *(Correspondance des skills)*

How Claude picks the [skill](#skill-skill) for a request. When Claude Code starts, it scans several locations for skills but only loads the name and description of each, not the full content. When you send a request, Claude compares your message against the descriptions of all available skills, using semantic matching: "explain what this function does" would match a skill described as "explain code with visual diagrams" because the intent overlaps. Once a match is found, Claude reads the complete SKILL.md file and follows its instructions. A skill with only a name, description, and instructions loads without asking you; if a skill pre-approves tools ([allowed-tools](#allowed-tools-allowed-tools)) or adds [hooks](#hook-hook), Claude Code may ask you to approve it first, depending on your permission mode.

### Skill priority *(Priorité des skills)*

Which [skill](#skill-skill) wins when two have the same name, as when you clone a repository that has a skill with the same name as one of your personal skills. The order: Enterprise ([managed settings](#managed-settings-paramètres-gérés), highest priority), then [personal skills](#personal-skills-skills-personnels) (your home directory), then [project skills](#project-skills-skills-de-projet) (the .claude/skills directory inside a repository). This lets organizations enforce standards through enterprise skills while still allowing individual customization: if your company has an enterprise "code-review" skill and you create a personal "code-review" skill, the enterprise version takes precedence. Skills from installed [plugins](#plugin-plugin) sit outside this order: they're namespaced as /plugin-name:skill-name, so a plugin skill and another skill with the same name both load. To avoid conflicts, use descriptive names: "frontend-review" or "backend-review" rather than just "review".

### Skill metadata fields *(Champs de métadonnées des skills)*

The fields of a [skill](#skill-skill)'s SKILL.md frontmatter. The agent skills open standard defines the core fields, and Claude Code adds many of its own, such as model. In Claude Code, every field is optional, and only description is recommended. Four are a good place to start: name identifies your skill and defaults to the directory name; description tells Claude when to use the skill, the most important field because Claude uses it for matching; [allowed-tools](#allowed-tools-allowed-tools) pre-approves the listed tools while the skill is active; model specifies which Claude model to use for the skill. If you upload the skill to Claude.ai or the Claude API, name and description are required: name limited to lowercase letters, numbers, and hyphens, up to 64 characters; description capped at 1,024 characters. Writing effective descriptions: be explicit (if someone told you "your job is to help with docs," you wouldn't know what to do, and Claude thinks the same way); a good description answers two questions, what does the skill do, and when should Claude use it; if your skill isn't triggering when you expect it to, try adding more keywords that match how you actually phrase your requests. The description is what Claude uses to decide whether a skill is relevant, so the language matters.

### allowed-tools *(allowed-tools)*

A [skill metadata field](#skill-metadata-fields-champs-de-métadonnées-des-skills) that pre-approves the tools it lists, so Claude can use them without a permission prompt for the rest of the turn that invoked the skill; the grant clears when you send your next message. Useful when a skill relies on the same handful of tools every time it runs, and you don't want to approve each call by hand. It doesn't limit Claude to those tools: if the skill's instructions lead Claude to edit or write a file, that goes through your normal permission settings like any other tool call. Listing Bash on its own pre-approves shell commands in general: reserve that for skills you trust, or narrow it to a pattern such as Bash(git status *). Omitted, nothing is pre-approved and Claude uses its normal permission model for every tool. To take tools away while a skill is active, a separate Claude Code frontmatter field, disallowed-tools, removes the tools you list from the set Claude can use.

### Progressive disclosure *(Divulgation progressive)*

How a larger [skill](#skill-skill) keeps its context use small. Skills share Claude's context window with your conversation: when Claude activates a skill, it loads the contents of its SKILL.md into context. Cramming everything into one long file takes up a lot of context window space, and it's not fun to maintain. So keep essential instructions in SKILL.md, and put detailed reference material in separate files that Claude reads only when needed; in SKILL.md, link to those supporting files with clear instructions about when to load them. A file linked for questions about system design never loads when someone asks where to add a component: like having a table of contents in the context window rather than the entire document. Rule of thumb: keep SKILL.md under 500 lines; past that, consider splitting the content into separate reference files. The open standard suggests organizing the skill directory with scripts/ (executable code), references/ (additional documentation) and assets/ (images, templates, or other data files). Scripts in the skill directory can run without loading their contents into context: the script executes and only the output consumes tokens. The key instruction in SKILL.md is to tell Claude to run the script, not read it. Useful for environment validation, data transformations that need to be consistent, and operations that are more reliable as tested code than generated code.

### CLAUDE.md *(CLAUDE.md)*

A file that loads into every conversation, always: best for always-on project standards. If you want Claude to use TypeScript strict mode in your project, put it in your CLAUDE.md file. Use it for project-wide standards that always apply, constraints like "never modify the database schema", and framework preferences and coding style. [Skills](#skill-skill), by contrast, load on demand: a PR review checklist doesn't need to be in context when you're writing new code, and activates when you ask for a review.

### Subagent *(Sous-agent)*

A Claude Code customization option that runs in a separate context: a subagent receives a task, works on it independently, and returns results, isolated from the main conversation. Subagents run in isolated execution contexts: use them for delegated work, where a [skill](#skill-skill) adds knowledge to your current conversation. Use subagents when you want to delegate a task to a separate execution context, need different tool access than the main conversation, or want isolation between delegated work and your main context. Subagents don't inherit skills automatically: a subagent doesn't see the skills you've already invoked. When you delegate a task to a subagent, it starts with a fresh, clean context, unless it's a fork, which starts with a copy of your conversation; a subagent that starts fresh can still find and invoke skills through the Skill tool, as long as it has that tool. Built-in agents (like Explore and Plan) don't preload skills. Custom subagents you define can preload the skills you list in their skills field; if you give one a tools list, keep Skill in it so the subagent can still invoke unlisted skills. Preloaded skills are loaded in full when the subagent starts, not on demand like in the main conversation. To create a custom subagent with skills, add an agent markdown file in .claude/agents (write it yourself or ask Claude to create it for you; if .claude/agents didn't exist when your session started, restart Claude Code to load the new subagent), and first make sure the skills exist in your .claude/skills directory. With both skills listed, a reviewer subagent applies them to every review. This pattern works well when you want isolated task delegation with specific expertise, when different subagents need different skills (frontend reviewer vs. backend reviewer), and when you want to enforce standards in delegated work without relying on prompts.

### Hook *(Hook)*

A Claude Code customization option that fires on events: a hook might run a linter every time Claude saves a file, or validate input before certain tool calls. Hooks are event-driven, where [skills](#skill-skill) are request-driven (they activate based on what you're asking). Use hooks for operations that should run on every file save, validation before specific tool calls, and automated side effects of Claude's actions.

### MCP server *(Serveur MCP)*

A Claude Code customization option that provides external tools and integrations: a different category entirely from [skills](#skill-skill).

### Plugin *(Plugin)*

A way to extend Claude Code with custom functionality designed to be shared across teams and projects. In your plugin project, create a skills directory that follows a similar file structure to the .claude directory: each [skill](#skill-skill) gets its own folder with a SKILL.md file inside. After you distribute your plugin to a [marketplace](#marketplace-marketplace), other users can discover and install it into Claude Code for themselves. Plugins let you distribute skills across repositories via marketplaces for broader community use: best when your skills aren't too project-specific and can be useful to community members beyond your immediate team. Plugin skills sit outside the [skill priority](#skill-priority-priorité-des-skills) order: they're namespaced as /plugin-name:skill-name, so a plugin skill and another skill with the same name both load.

### Marketplace *(Marketplace)*

Where you distribute a [plugin](#plugin-plugin): once it's there, other users can discover and install it into Claude Code for themselves. Claude Code's Discover plugins view is a searchable list of plugins from claude-plugins-official with install counts. [Managed settings](#managed-settings-paramètres-gérés) control which marketplaces people can add and install plugins from (strictKnownMarketplaces).

### Managed settings *(Paramètres gérés)*

How administrators deploy [skills](#skill-skill) organization-wide. Each skill goes in .claude/skills/ inside the managed settings directory on each machine, for example /etc/claude-code/.claude/skills/ on Linux. Enterprise skills take the highest priority: they override personal and project skills with the same name ([skill priority](#skill-priority-priorité-des-skills)). Managed settings also control [plugins](#plugin-plugin): strictKnownMarketplaces limits which [marketplaces](#marketplace-marketplace) people can add and install plugins from, each entry a source (a GitHub repo, or the URL of a marketplace.json). Enterprise deployment is the right choice for mandatory standards, security requirements, compliance workflows, and coding practices that must be consistent across the organization: the keyword here is "must".
