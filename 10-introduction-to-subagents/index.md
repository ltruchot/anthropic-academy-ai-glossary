## Glossaire

### Subagent *(Sous-agent)*

A specialized assistant that Claude Code can delegate tasks to: think of it as a focused helper. Each one runs in its own conversation context window, does its work, and returns a summary to the main thread; the intermediate steps (all the file reads, searches, and tool calls) stay isolated and never clutter your main conversation. As the [main context window](#main-context-window-fenêtre-de-contexte-principale) fills up, subagents solve this by spinning up a separate context window. A subagent's starting context includes a custom system prompt from your configuration file, which defines its role and behavior, and a task description written by the parent agent based on what you asked for. The subagent then works on its own: it reads files, runs searches, edits code, whatever it needs to do. When it's done, only a summary comes back to your main conversation; Claude Code saves the rest of the subagent's conversation in a separate transcript file. Your main context stays clean: you get the answer without all the noise of the journey it took to find it. The tradeoff: your main conversation doesn't see how the subagent reached its conclusions. Say you want to know which service handles refunds in an unfamiliar codebase: you ask the question, the Explore subagent spins up, does all the digging in its own context, and hands back a focused answer. Subagents give you three main benefits: they break work into focused pieces, letting each subagent concentrate on a specific task; they keep your main context window clean by isolating all the [intermediate work](#intermediate-work-travail-intermédiaire); they bring back just the information you need as a concise summary. Claude Code ships with [built-in subagents](#built-in-subagents-sous-agents-intégrés), and you can create a [custom subagent](#custom-subagent-sous-agent-personnalisé) of your own. Either way, they're a practical way to get more out of longer Claude Code sessions.

### Main context window *(Fenêtre de contexte principale)*

The context window of your main conversation with Claude Code. Every time you chat with Claude Code, you're adding to it: every tool call, every file read, every search result gets stored there. That space is finite, and once it fills up, Claude starts losing track of earlier parts of the conversation. Say you're exploring an unfamiliar codebase and you want to know which service handles refunds: without a [subagent](#subagent-sous-agent), Claude might read 15 files, run several searches, and trace through multiple function calls, and all of that fills your context window, even though you only needed one fact; with a subagent, your main context window only records the question and the summary, not the files read along the way. The less noise in your main context, the longer and more effectively you can work.

### Built-in subagents *(Sous-agents intégrés)*

The [subagents](#subagent-sous-agent) Claude Code ships with, several of them, which you can use right away, among them: the general purpose subagent, for multi-step tasks that require both exploration and action; Explore, for fast searching and navigation of codebases; Plan, used during plan mode for research and analysis of your codebase before presenting a plan. Beyond these built-in options, you can create a [custom subagent](#custom-subagent-sous-agent-personnalisé).

### Custom subagent *(Sous-agent personnalisé)*

A [subagent](#subagent-sous-agent) you create yourself, beyond the [built-in options](#built-in-subagents-sous-agents-intégrés), with a custom system prompt and tool access: a specialized agent tailored to your workflow, such as a code reviewer, a test writer, a documentation generator, or anything else you need. Custom subagents specialize in specific tasks, like reviewing code, writing tests, or checking documentation. Each is defined as a markdown file with YAML frontmatter that tells Claude when to use the subagent and how the subagent should behave: its [config file](#subagent-config-file-fichier-de-configuration-dun-sous-agent). The easiest way to create one is to ask Claude to write it for you: describe the subagent you want and where to save it, and Claude writes the file (the /agents wizard was removed in Claude Code v2.1.198). You still choose a scope, tools, a model, and a color: include those choices in your request. Its scope comes from where its file is: a file in .claude/agents/ is project-level, available only in the current project; a file in .claude/agents/ in your home directory is user-level, shared across all projects on your machine. You can write the configuration manually, but the recommended approach is to let Claude generate it: Claude produces a name, description, and system prompt based on your input. A code reviewer subagent is tested by making some code changes and asking Claude to review them; if the agents folder didn't exist when your session started, restart Claude Code first to load the new subagent. If it is not being used when you expect it to be, check its [description](#subagent-description-description-dun-sous-agent). A subagent that's poorly configured will wander, run too long, or produce output the main agent can't use; effective subagents share four characteristics: specific descriptions, structured output and obstacle reporting (both in the [output format](#output-format-format-de-sortie)), and [limited tool access](#limited-tool-access-accès-limité-aux-outils).

### Subagent config file *(Fichier de configuration d'un sous-agent)*

The markdown file that defines a [custom subagent](#custom-subagent-sous-agent-personnalisé), saved in the folder for the scope you chose (for a project-level subagent, typically .claude/agents/your-agent-name.md). Its YAML frontmatter holds its fields, as in a typical subagent config: name, a unique identifier for the subagent, which is how you reference it, either by asking Claude directly or by typing @agent- followed by the name in your message; [description](#subagent-description-description-dun-sous-agent), which controls when Claude decides to use the subagent; tools, which lists which tools the subagent can access (Claude fills it in from your request, but you can edit the list at any time); model, which specifies which Claude model to use: an alias (sonnet, opus, haiku, or fable), a full model ID such as claude-sonnet-5, or inherit; color, the UI color for identifying the subagent, so you can quickly tell which subagent is active. Think about what your subagent actually needs: a code reviewer probably does not need edit tools, since it should read and analyze code, not change it, though you might keep execution tools enabled so it can more easily identify pending changes. Give it only the tools it needs: [limited tool access](#limited-tool-access-accès-limité-aux-outils). For the model, the options include: Haiku, best for fast, lightweight tasks; Sonnet, a good middle ground between speed and depth; Opus, best for complex analysis; Inherit, which uses whatever model your main conversation is running. The body of the file (everything below the YAML frontmatter) is the system prompt: the subagent's instructions, what it should focus on, how it should analyze things, and how it should report findings back to the main agent. A well-written system prompt is the difference between a useful subagent and one that misses the point: be specific about what the subagent should look for and how it should structure its output.

### Subagent description *(Description d'un sous-agent)*

The description field of a [subagent's config file](#subagent-config-file-fichier-de-configuration-dun-sous-agent): it controls when Claude decides to use the subagent. It must be a single line (use escaped newline characters \n if you need breaks). If you want Claude to delegate tasks to the subagent without you explicitly asking, include the word "proactively" in it. You can also add example conversations to it, to help Claude understand specific scenarios where the subagent should be used: the more concrete your examples, the better Claude gets at knowing when to delegate. If the subagent is not being used when you expect it to be, go back and check the description: more specific examples and trigger scenarios help Claude understand when to delegate work to your subagent. When you send a message to the main context window agent, the name and description of every available subagent are included in the system prompt: this is how the main agent decides which subagent to launch and when, so the name and description are what you should tweak for better control over when a subagent gets triggered automatically. The description also plays a second role: the main agent uses it as guidance for writing the [input prompt](#input-prompt-prompt-dentrée) that kicks off the task. So the description doesn't just control when a subagent runs, it shapes what the subagent is told to do: write it to steer both.

### Input prompt *(Prompt d'entrée)*

The prompt the main agent writes to kick off the task when it launches a [subagent](#subagent-sous-agent). It uses the subagent's [description](#subagent-description-description-dun-sous-agent) as guidance for writing that prompt. For a code review subagent with a generic description, the main agent might write an input prompt like "use git diff to find the current changes": that's vague, and the subagent has to figure out which files matter on its own. If the description includes something like "You must tell the agent precisely which files you want it to review," the main agent writes a much more specific input prompt that lists the actual files to review. The same technique works across different types of subagents: adding "return sources that can be cited" to a web search subagent's description causes the main agent to include that instruction when delegating the task.

### Output format *(Format de sortie)*

The format a [subagent](#subagent-sous-agent)'s system prompt defines for its output: the single most important improvement you can make to a subagent. It creates natural stopping points (the subagent knows it's done when it has filled in each section of the format) and prevents the subagent from running too long: without a defined output, subagents struggle to decide when enough research has been done and tend to run much longer than necessary. A structured format for a code review subagent, for example: Summary, Critical Issues, Major Issues, Minor Issues, Recommendations, Approval Status; once every section is filled in, the subagent knows it can stop. Obstacle reporting belongs in it too: when a subagent discovers a workaround during its work, like solving a dependency issue or finding that a certain command needs particular flags, those details need to appear in the summary it returns; if they don't, the main thread has to rediscover the same solutions on its own, which wastes time and tokens. The kinds of things you want surfaced include setup issues or environment quirks, workarounds discovered during the task, commands that needed special flags or configuration, dependencies or imports that caused problems. The way to get them is to ask for them explicitly: an "Obstacles Encountered" section in the output format surfaces this information reliably. With a structured output, the subagent knows when it's done and returns information the main thread can use.

### Limited tool access *(Accès limité aux outils)*

Giving a [subagent](#subagent-sous-agent) only the tools it actually needs (the tools field of its [config file](#subagent-config-file-fichier-de-configuration-dun-sous-agent)): not every subagent needs access to every tool. Think about what a subagent actually needs to do, and only give it the tools required for that job. This prevents unintended side effects, and it makes each subagent's role clearer when you have several of them. A research / read-only subagent only needs Glob, Grep, and Read: it cannot accidentally modify files. A code reviewer needs Bash access to run git diff and see what changed, but still doesn't need Edit or Write. A styling or code modification agent is where you give Edit and Write access, because the subagent's job is to actually change your code.

### Intermediate work *(Travail intermédiaire)*

The steps a task takes on its way to its result: the file reads, searches, and tool calls a [subagent](#subagent-sous-agent) keeps isolated from your main thread. Whether it matters to your main thread is the difference between a subagent that helps and one that gets in the way, and the decision rule: ask yourself one question, does the intermediate work matter? If the answer is no (you just need the final result), delegate it to a subagent; if the answer is yes (you need to see and react to what's happening along the way), keep it in your main thread. Subagents work best when the exploration is separate from the execution; if each step in a task depends on what the previous step discovered, you want that work in your main thread. They excel at tasks where you need a result, not a play-by-play of how it was found; where the exploratory work would clutter your main thread's context; where the task benefits from a fresh perspective or a custom system prompt. Research is the classic subagent use case: say you investigate how authentication works in an unfamiliar codebase; your main thread needs to know where the JWT is validated, but it doesn't need to see every file that was searched along the way; a research subagent can read dozens of files, trace through function calls, and explore different code paths, and all that exploration stays in its context. Code reviews: Claude reviews code more effectively when the code is presented as being authored by someone else; if you built a feature over many turns with your main thread, asking that same thread to review it often produces weak feedback, since Claude was involved in creating it and has trouble seeing it with fresh eyes. A reviewer subagent sees the changes in a separate context: it runs git diff, reads the modified files, and applies its specialized review criteria without the history of how the code was written, and its system prompt can encode project-specific review standards, ensuring consistent review criteria across the team. Custom system prompts: Claude Code's default system prompt emphasizes concise, code-focused responses, which works great for coding, but not for everything. A copywriting subagent gets instructions about tone, audience, and style (the default prompt tends toward concise technical writing, not what you want for a landing page or email campaign); a styling subagent is told in its system prompt to read your design system files first, so it knows your color variables, spacing conventions, and component patterns before it starts writing any CSS. Where a subagent hurts: its [anti-patterns](#subagent-anti-patterns-anti-patterns-des-sous-agents).

### Subagent anti-patterns *(Anti-patterns des sous-agents)*

The three common ways a [subagent](#subagent-sous-agent) hurts. The overhead of launching a subagent (hiding its work from the main thread and compressing its findings into a summary) only makes sense when the subagent does something the main thread can't. Expert claims: subagents that claim expertise rarely help; prompts like "you are a Python expert" or "you are a Kubernetes specialist" add no value because Claude already has that knowledge, and there's nothing a so-called expert subagent can do that your main thread can't do directly. Sequential pipelines: consider a three-agent flow, one to reproduce a bug, one to debug it, and one to fix it; pipelines work when tasks are truly independent, and fail when each step depends on discoveries from the previous step, as bug fixing almost always does: information gets lost in the handoff between agents. Test runners: test runner subagents tend to hide information you need; when tests fail, you want the full output to diagnose issues, and a subagent that returns "tests failed" forces you to create additional debug scripts to get details that would have been visible in direct output. Testing has shown that the test runner pattern performed worst among all configurations. Whether to delegate at all: does the [intermediate work](#intermediate-work-travail-intermédiaire) matter?
